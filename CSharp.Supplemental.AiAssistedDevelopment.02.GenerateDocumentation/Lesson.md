# Generate Documentation Using GitHub Copilot Tools

## What This Is

This section adapts the documentation material from the Microsoft Learn GitHub Copilot training path. Copilot can explain code, draft XML comments, summarize project structure, and produce README material. That is genuinely useful. It also happily writes documentation that sounds authoritative while documenting what it assumes the code does, which is less useful unless your documentation standard is "vibes in business casual."

Documentation generated by AI should be reviewed against three things:

- The actual code.
- The intended audience.
- The maintenance burden of keeping the words true.

---

## Before You Start

Open a scratch C# file with Copilot enabled. In this chapter, the runner shows the finished examples, but your editor is where you practice asking Copilot to explain, document, and revise. Keep the lesson runner open beside the editor so you can compare generated documentation against executable behavior.

The workflow is:

1. Ask Copilot to explain selected code first.
2. Correct misunderstandings before asking it to document the code.
3. Tell it the audience and format: XML comments, README, architecture note, or inline comment.
4. Remove obvious comments.
5. Check exceptions, side effects, null behavior, and domain assumptions.

Good documentation should reduce future confusion. It should not give every line of code a tiny decorative hat.

## Step 1: Document a Method

Start by typing the method without XML comments:

```csharp
private static decimal SumValidAmounts(IEnumerable<string> rows)
{
    if (rows == null)
        throw new ArgumentNullException(nameof(rows));

    return rows
        .Where(row => !string.IsNullOrWhiteSpace(row))
        .Select(row => decimal.TryParse(row, out decimal value) ? value : 0m)
        .Sum();
}
```

Select the method and ask Copilot:

```text
Generate XML documentation comments for this method. Focus on the method contract: null input, ignored rows, unparsable rows, and the return value. Do not describe each line of code.
```

Review the generated comments before accepting them. The useful comments should describe behavior a caller needs to know. If Copilot writes "uses LINQ to sum rows," ask it to try again. That comment is not wrong, exactly, but neither is labeling a door "rectangular wall hole."

> **Screenshot placeholder:** Add an image showing Copilot's XML documentation suggestion above `SumValidAmounts`.

Run Step 1 in the lesson runner. Compare the runner's XML comments to the ones Copilot generated for you.

Good generated XML comments should answer:

- What does the method promise?
- What inputs are accepted?
- What inputs throw?
- What inputs are ignored?
- What does the return value mean when no valid data exists?

The comments are part of the public contract. If they lie, the codebase now has two bugs: the behavior and the map to the behavior.

## Step 2: Explain Before Documenting

Before asking Copilot to document code, ask it to explain the code. If the explanation is wrong, the documentation will be wrong with punctuation.

Type or paste the `Invoice` class and `CalculateTotal` method from the runner sample into your scratch file. Select only `CalculateTotal` and ask:

```text
Explain what this method does in plain English. Mention the tax calculation, the preferred-customer discount, and the null behavior. Do not write XML comments yet.
```

Read the explanation like a reviewer. It should say that total equals subtotal plus tax, minus a 10% subtotal discount for preferred customers. It should not imply the discount applies to subtotal plus tax unless the code actually does that.

> **Screenshot placeholder:** Add an image showing Copilot Chat explaining `CalculateTotal`.

If the explanation is accurate, follow up:

```text
Now generate XML documentation comments for CalculateTotal based only on that behavior. Keep the comments concise.
```

Run Step 2 in the lesson runner and compare the printed explanation to Copilot's answer. The habit to build is not "make Copilot write docs." The habit is "make Copilot prove it understands the code before it writes docs." This prevents beautifully phrased documentation for behavior that does not exist, which is less charming in a production codebase.

## Step 3: Remove Decorative Comments

AI-generated comments often explain syntax instead of intent. In this step, you will intentionally ask for too much commenting, then clean it up.

Paste this method into your editor:

```csharp
private static IEnumerable<string> GetBillableDocumentIds(IEnumerable<string> documentIds)
{
    foreach (string documentId in documentIds)
    {
        if (documentId.StartsWith("VOID-", StringComparison.OrdinalIgnoreCase))
            continue;

        yield return documentId;
    }
}
```

Ask Copilot:

```text
Add comments to this method for a junior developer.
```

It will likely add comments that explain the loop and the `yield return`. Read them, sigh gently if needed, and then ask:

```text
Remove obvious comments and keep only a comment explaining the non-obvious business rule for VOID rows.
```

> **Screenshot placeholder:** Add an image showing the before-and-after comment cleanup.

Run Step 3 in the lesson runner. Notice that the final version keeps one comment: why `VOID-` rows are skipped. That is the part a maintainer cannot infer from syntax alone.

Keep comments that explain:

- A business rule.
- A non-obvious trade-off.
- A workaround for a known external behavior.
- A security or compliance constraint.
- Why the obvious implementation is not being used.

Remove comments that merely restate the next line of code. The code already has the floor.

## Step 4: Generate a README Summary

Copilot is useful for first-draft README material when you give it real project facts. Vague prompts produce vague README sections, often with a suspicious number of "seamless" experiences nobody ordered.

In Copilot Chat, provide concrete metadata:

```text
Draft a short README summary for a C# console utility named Document Import Validator.

Facts:
- Purpose: validates imported document rows before they enter workflow.
- Capabilities: CSV row validation, amount parsing, duplicate document detection.
- Audience: internal developers and support analysts.
- Do not invent setup steps, deployment details, dashboards, or authentication features.
```

Review the draft. It should be specific and modest. If Copilot adds features that are not in the facts, ask it to remove unsupported claims.

> **Screenshot placeholder:** Add an image showing the README draft in Copilot Chat.

Run Step 4 in the lesson runner. The code renders a README-style summary from structured metadata. Change the metadata in your scratch file and rerun it. Notice how concrete inputs produce concrete documentation. Shocking, I know. Requirements remain annoyingly relevant.

When asking Copilot for README content, include:

- The project name.
- The project purpose.
- The intended audience.
- The supported workflows.
- Local setup or usage requirements.
- Anything the README should not claim.

The final review is simple: if the README says something the codebase cannot back up, delete it.
