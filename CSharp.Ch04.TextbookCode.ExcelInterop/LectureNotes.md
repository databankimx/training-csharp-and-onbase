# Ch04 Textbook Code: Excel Interop

## What This Is

The WinForms original of the demo already ported into `ExcelInterop()` in `CSharp.Ch04.UsingTypes`. This form opens Excel, writes headers and the first 10 squares into a worksheet, and auto-fits the columns, all in `Form1_Load()`, no button, no interaction, just watch Excel pop up.

No bugs. This one required a real project-file and tooling decision, though, in two stages.

---

## Why This Project's .csproj Looks Different From Every Other Lab

Every other project in this training set that references Excel interop (`CSharp.Ch04.UsingTypes`) uses the `Microsoft.Office.Interop.Excel` NuGet package as a clean `PackageReference`. That package doesn't get the "embed interop types" treatment a real COM reference gets, which means members like `Worksheets[1]` and `Cells[row, col]` come back as plain `object` instead of their real COM types, forcing the code to use `dynamic` to compile.

This lab's original download uses fully statically-typed code, `Excel.Worksheet sheet = workbook.Worksheets[1];`, no `dynamic` anywhere. To keep that code untouched, the `.csproj` here uses a real `<COMReference>` instead, generated by Visual Studio's **Add > COM Reference** dialog against the Excel Object Library actually registered on the machine:

```xml
<COMReference Include="Microsoft.Office.Interop.Excel">
  <WrapperTool>tlbimp</WrapperTool>
  <VersionMinor>9</VersionMinor>
  <VersionMajor>1</VersionMajor>
  <Guid>00020813-0000-0000-c000-000000000046</Guid>
  <Lcid>0</Lcid>
  <Isolated>false</Isolated>
  <EmbedInteropTypes>true</EmbedInteropTypes>
</COMReference>
```

This is meaningfully different from a raw `<Reference><EmbedInteropTypes>True</EmbedInteropTypes></Reference>` pointing at a pre-built Primary Interop Assembly (which is what an earlier version of this file, and this note, incorrectly assumed). A `<COMReference>` with `WrapperTool=tlbimp` generates the interop wrapper **on the fly at build time**, straight from Excel's own registered COM type library (identified by that `Guid`), which is why it worked even though no formal PIA was ever installed on this machine, modern Office doesn't ship one by default, and this project doesn't need one.

## The Real Gotcha: `<COMReference>` Can't Build via `dotnet build`

This project builds and runs fine from Visual Studio, but running it through `LessonRunner` (which normally shells out to `dotnet run` for every lesson) failed with:

```
error MSB4803: The task "ResolveComReference" is not supported on the .NET Core version of MSBuild.
Please use the .NET Framework version of MSBuild.
```

This isn't a machine configuration problem, it's a hard tooling limitation. The cross-platform `dotnet` SDK CLI ships its own MSBuild, and that MSBuild has never implemented the `ResolveComReference` task, the one responsible for running `tlbimp` and processing `<COMReference>` items. Only the full .NET Framework MSBuild that ships with Visual Studio can build a project with a `<COMReference>` in it. No amount of PIA installation, GAC registration, or version tweaking fixes this, `dotnet build` simply cannot do it, on any machine.

`LessonRunner` handles this by branching on a `RequiresFullFrameworkMsBuild` flag on the `Lesson` model. For lessons with that flag set, instead of `dotnet run`, it locates Visual Studio's `MSBuild.exe` via `vswhere.exe` (installed alongside any VS 2017+ install), invokes that directly to build the project, then launches the resulting `.exe` itself. Every other lesson in this training set is unaffected, this path only exists for projects with a real COM reference.
