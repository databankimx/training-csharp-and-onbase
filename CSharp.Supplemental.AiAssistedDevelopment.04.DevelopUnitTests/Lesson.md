# Develop Unit Tests Using GitHub Copilot Tools

## What This Is

This section adapts the Microsoft Learn module on generating unit tests with Copilot. Copilot is very good at making tests appear. It is less reliable at making tests matter.

A generated test suite often looks tidy: arrange, act, assert; friendly method names; green output. The question is whether it verifies the requirement or merely confirms the current implementation. Tests that worship the implementation are not a safety net. They are a decorative rug over a hole in the floor.

---

## Before You Start

The lesson runner does not host NUnit directly, so the runnable steps use tiny hand-rolled assertion harnesses. In a real codebase, you would ask Copilot to use the repository's actual test framework and naming conventions.

For each step, practice the Copilot workflow in a scratch test file:

1. Show Copilot the method under test.
2. State the required behaviors.
3. Ask for tests in the local style.
4. Review for missing cases.
5. Run the equivalent sample in the lesson runner.

## Step 1: Review Test Coverage

Start with the method:

```csharp
private static int SumPositiveNumbers(int[] numbers)
{
    if (numbers == null)
        throw new ArgumentNullException(nameof(numbers));

    int sum = 0;
    foreach (int number in numbers)
        if (number > 0)
            sum += number;

    return sum;
}
```

Ask Copilot:

```text
Generate NUnit tests for SumPositiveNumbers.

Required coverage:
- Sums multiple positive numbers.
- Ignores zero and negative numbers.
- Handles a single positive number.
- Throws ArgumentNullException for null input.
- Use clear test names and meaningful assertions.
```

Do not accept the first suite just because it compiles. Check whether every required behavior has a test. If Copilot gives you five tests that all amount to "does not return null," smile politely, delete most of them, and ask for boundary and failure cases.

Run Step 1 in the lesson runner. The runner sample uses `AssertEqual` and `AssertThrows` so the behavior can execute in a console app. Compare that coverage shape to the NUnit tests Copilot generated.

The bar is simple: each test should prove a requirement that matters. A green test that proves nothing is a very small decorative lamp.

## Step 2: Boundary Tests

Generated tests often cover ordinary inputs and forget the edges. This step tests a discount rule at the boundaries: `0`, `1`, and invalid values outside the range.

Give Copilot the method contract first:

```text
Generate NUnit tests for a method ApplyDiscount(decimal price, decimal discountPercentage).

Behavior:
- A discount of 0 returns the original price.
- A discount of 1 returns zero.
- A discount below 0 throws ArgumentOutOfRangeException.
- A discount above 1 throws ArgumentOutOfRangeException.
- Use boundary-focused test names.
```

Then compare Copilot's output against the runner sample. The runner executes the same logic with a small assertion harness.

> **Screenshot placeholder:** Add an image showing the boundary tests generated by Copilot.

Run Step 2 in the lesson runner and check the cases:

- `0` discount returns the original price.
- `1` discount returns zero.
- A negative discount throws.
- A discount greater than `1` throws.

When asking Copilot for tests, name the boundaries explicitly. Otherwise it may produce a test suite that smiles warmly and avoids all conflict.

Boundary tests are especially important for generated code because the implementation often looks reasonable at a glance. The edge is where "reasonable" goes to find out whether it has been lying to itself.

## Step 3: Exception Tests

Exception tests should verify the exception that matters. A generated test that catches `Exception` proves almost nothing, except possibly that the test is afraid of commitment.

Start with this method:

```csharp
private static string NormalizeDocumentType(string documentType)
{
    if (string.IsNullOrWhiteSpace(documentType))
        throw new ArgumentException("Document type is required.", nameof(documentType));

    return documentType.Trim().ToUpperInvariant();
}
```

Ask Copilot:

```text
Generate NUnit tests for NormalizeDocumentType.

Tests must verify:
- Whitespace input throws ArgumentException.
- The exception ParamName is documentType.
- Valid input is trimmed and uppercased invariantly.
- Do not catch base Exception.
```

> **Screenshot placeholder:** Add an image showing Copilot's exception test, especially the assertion for `ParamName`.

Run Step 3 in the lesson runner. The sample verifies both exception type and parameter name.

For real NUnit tests, prefer assertions that verify:

- The exact exception type.
- The parameter name for argument exceptions.
- Any domain-specific error code or message your project requires.
- That valid input does not throw.

Do not let generated tests flatten every error path into "something bad happened." Production will provide that insight for free. Tests should be more specific.

## Step 4: Weak Tests Miss Mutations

One way to evaluate test quality is to imagine a broken implementation. Would the test catch it?

Ask Copilot:

```text
Review these tests for strength. Would they catch an implementation that forgot to uppercase the type and forgot to pad the ID? If not, improve them.
```

Then show it this intended behavior:

```text
FormatKey("ap", 123) must return AP-000123.
```

Copilot should generate or improve a test that checks exact output, not merely non-null output.

> **Screenshot placeholder:** Add an image showing Copilot revising a weak test into an exact behavior test.

Run Step 4 in the lesson runner. The sample compares a correct implementation with a mutated one:

- `FormatKeyCorrect` trims, uppercases, and pads the ID.
- `FormatKeyMutated` skips uppercasing and padding.

If your generated tests cannot tell those apart, they are testing theater. Very nice curtain, no building behind it.

When Copilot generates tests, try this review move: intentionally describe one likely bug and ask whether the test suite would catch it. If the answer is no, ask for stronger tests before trusting the suite.
